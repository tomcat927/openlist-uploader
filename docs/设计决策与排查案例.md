# 设计决策与排查案例

> 日常使用与问题排查中沉淀下来的机制说明、设计取舍和真实排查案例。忘了某个功能"为什么这么做"或"出了问题怎么查"时，先来这里翻。

## 一、功能机制速查

### 1. 上传完成后本地加 delete- 前缀（设置开关，默认开）

文件夹批次全部上传成功后，本地文件夹改名为 `delete-原名`（单文件拖入则改文件名，文件夹内部的文件一律不动），表示可删除。

**改名触发条件（三条判据缺一不可）**：

1. 该文件夹批次的任务全部成功（或已手动标记"已处理"）；
2. 队列中没有路径落在该文件夹下的其他任务（防止改断单独拖入的同目录文件）；
3. 没有未处理的拦截记录（有文件被拦 = 没传完 = 不标记）。

**保护措施**：

- 完整路径加前缀后超过 259 字符 → 跳过不标记（资源管理器按 MAX_PATH=260 处理，超长后连删除都困难）；
- 目标已存在 → 自动加序号（`delete-A-1`）；
- 文件夹被占用（资源管理器开着、杀软扫描）→ 延迟重试 5s/20s 两次后放弃，只在日志记录；
- 名称超 255 字符 → 跳过（实际上传过的文件名都被入队校验限制在 175 字节内，几乎不会触发）。

日志关键字：`已标记上传完成(可删除)`、`delete- 标记跳过`。

### 2. 待清理 Tab

- 批次完成时把摘要（路径/文件数/总大小）写入 `cleanup.json`，**与 delete- 开关解耦**：关掉改名，清单照样生成；
- "移入回收站"走系统回收站（可恢复）。**注意：超过回收站容量的项目会被 Windows 直接永久删除**，不会进回收站——确认弹窗里有提示；
- 同一文件夹再次完整上传会覆盖合并旧记录（按原始路径去重）；
- 只对本功能上线后新完成的批次生效，历史批次靠 delete- 前缀在资源管理器里辨认。

### 3. 历史记录

- **状态筛选**：全部/成功/失败按钮，计数是后端全量统计（不受当前筛选影响）；
- **重试**：单条"重试"和工具栏"重试全部失败"都是把失败记录重新入队。批量重试只处理**本地文件仍存在**的记录（磁盘没接回时点了不会白失败），已在队列的自动跳过，已标记"已处理"的不参与；
- **"已在队列"徽章**：失败记录对应的任务正在队列中（排队/上传中）时自动显示，重试按钮同时禁用。这是前端实时比对队列得出的派生状态，不落盘，任务完成自动消失；
- **重传成功后旧失败记录会被替换**：历史按"本地路径 + 目标路径"去重，重传完成时旧失败记录被移除、插入新的成功记录，不会并存。重传到不同目标路径则两条都保留（确实是两次不同上传）；重传再次失败则失败记录刷新为最新一次的错误和时间；
- **为什么重试成功后不从历史删除记录**：历史是审计日志，完成时的自动替换已经解决了"重复感"；删记录会让失败痕迹断档。

### 4. 同名文件策略：推荐"覆盖"

| | 跳过 | 覆盖（推荐） |
|---|---|---|
| 判重依据 | 只看文件名 | 文件内容（SHA1） |
| 同名同内容 | 跳过，零流量 | 秒传，几乎零流量 |
| 同名不同内容 | **静默跳过并标记完成（危险）** | 覆盖云端为最新内容 |
| 额外开销 | 无 | 上传前本地算一次 SHA1（只读磁盘，2GB 约几秒） |

**为什么覆盖更适合本工具**：配合"传完就删本地"的流程，跳过模式下同名不同内容的文件会被静默跳过，用户以为传好了、把本地删了——新内容永久丢失。覆盖模式从机制上消除这类静默丢失。秒传是否命中只取决于 115 服务端有没有相同内容（SHA1），与目标目录无关。

### 5. 重复上传会耗流量吗

- 上传端 → OpenList 走本机回环（127.0.0.1），不算外网流量；外网只有 OpenList → 115 这一段；
- 重复上传同文件到同位置：跳过模式零流量（按名跳过）；覆盖模式秒传零流量（按内容）；
- 真正耗流量的情形：内容变了（覆盖模式全量重传）、或文件名不同但内容相同（跳过模式不看内容，会当新文件全量传——此时换覆盖模式可秒传）。

### 6. 设置页实时自动保存

- 无保存按钮，任何改动 800ms 防抖后自动持久化；界面显示"已自动保存 时间"；
- 上传目标目录、限速等之前"半自动保存"的字段也统一走这套，行为一致；
- 配置以表单为唯一数据源，保存后回填不会触发二次保存。

### 7. 防误点设计

- "清空所有记录"（拦截记录）、"清空历史"均有二次确认弹窗；
- 危险按钮（清空/移入回收站）在工具栏最右侧，与搜索框的 ✕ 拉开距离；
- 原则：重后果动作必须显式确认 + 与高频轻量动作在空间上分离。

## 二、排查案例：upload reach the limit（2026-10-03）

**现象**：`/115Crypt/海*/01` 下的 9.86GB zip 六次尝试全部失败，OpenList 网页后台显示 `upload reach the limit`，但软件错误只有"后台上传任务已消失，但目标目录中未找到文件"，日志里搜不到这个字符串。

**结论：两个叠加的 bug + 一个 115 限制，全部已修复。**

### Bug 1：5GB 大文件保护被过期元数据绕过

拖入文件夹时 zip 还在写入中（当时 2.62GB），入队记录了这个大小；执行上传时文件已长到 9.86GB，但拦截检查用的是入队元数据 → 放行 → 115 在后台转存阶段静默拒绝（非会员单文件 5GB 上限）。

日志证据（三行对照）：

```
开始上传:   size=2810770313B   ← 入队元数据（2.62GB，<5GB 放行）
文件已打开: size=10591448829B  ← 磁盘实际（9.86GB）
```

**修复**：每次执行上传前从磁盘读实际大小刷新任务元数据，不一致时记日志"文件大小与入队时不一致，以磁盘实际大小为准"。

### Bug 2：失败原因查询端点返回的是网页

后台任务消失后，软件会查任务列表找失败原因，但用的端点是 `/api/task/upload`——这版 OpenList 没有这个 API，请求落到前端 SPA 路由返回了 3483 字节的 index.html（status=200），JSON 解析必然失败 → 永远拿不到真实错误，`api_response` 为空。

日志证据：`Alist 全部上传任务响应: status=200 OK, body_length=3483` + `error=expected value at line 1 column 1, body=<!doctype html>`。

**修复**：改查 `/api/task/upload/done`（与 undone 同组、实测可用，含失败原因）；拿不到错误原文时把排查结论（任务 ID、查询接口、结果）写进 `api_response`；文件 >4GB 时错误信息追加 115 限制提示与操作建议。同时响应异常时日志只记录前 200 字符，避免整页 HTML 灌进日志。

### 115 的行为认知

`upload reach the limit` 是 115 驱动上报的限制（大文件/频率），发生在**后台转存阶段**：提交接口返回成功、任务几秒内从待完成列表消失、目标目录不出现文件。重试撞不过去，必须前置拦截——这正是大文件保护 + 分卷压缩存在的意义。

### 经验教训

1. **"提交接口成功"≠上传成功**：as_task 模式下提交只是开始，结果要看任务列表；
2. **大文件必须在入队/执行前拦**（且用磁盘实际大小），不能指望 115 报错；
3. 排查上传问题先做三行对照：`配置快照`（开关状态）+ `开始上传`（元数据 size）+ `文件已打开`（磁盘 size）。

## 三、日志排查速查

日志位置：本机 `%LOCALAPPDATA%\openlist-uploader\logs\alist-YYYY-MM-DD.log`（按天）+ `debug.log`（全量）；开启日志同步后，远程 Alist 有原文与 `-redacted` 脱敏两份。

| 要查什么 | 搜索关键字 | 说明 |
|---|---|---|
| 当时各开关的状态 | `配置快照` | 启动（startup）/保存配置（config_saved）/每天第一条（daily_rotate）各一条 |
| 接口原始返回值 | `raw=` | 仅 API 直接拒绝类错误（ApiWithResponse）有 |
| 后台任务失败原因 | `查到失败任务错误` | 修复后从 done 列表取，同步写入 api_response |
| 本地文件不存在 | `os error 3` | 磁盘未接、文件被移走/改名 |
| delete- 标记结果 | `已标记上传完成` / `delete- 标记跳过` | 跳过原因跟在后面 |
| 5GB 拦截 | `大文件保护拦截` | 拦截发生在打开文件之前 |
| 文件大小元数据过期 | `文件大小与入队时不一致` | 已按磁盘实际大小执行 |
| 批量重试结果 | `批量重试失败记录` | 三个计数：入队/已在队列/文件缺失 |

**脱敏版说明**：`file=`、`alist_path=` 等键的值替换为 `[N1]` 编号占位符（同一文件全程同号，保持关联性），错误信息里的连续中文段也会替换；需要还原时拿原文日志对照编号。
